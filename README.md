## 《月圆之夜》卡牌图鉴

这个仓库收集了《月圆之夜》游戏中经典模式和小红帽日记模式下的绝大部分卡牌，用于线上浏览和实体打印。

## 文件说明

**主要代码文件说明：**

- `card_capture.py`：用于自动化从游戏图鉴中提取卡牌贴图
- `cap1CardinGame.py`：用于手动从游戏内截取卡牌贴图

**`assets` 文件夹下各目录说明：**

- `assets_extract`：从游戏中提取的部分 unity 贴图资源
- `bookCover`：根据 tb 店铺的卡册尺寸重新排版的卡册封面
- `card_base`：经典模式图鉴中“全部”选项收录的卡牌（仅收录满星卡牌），共 696 张
- `card_base_extra`：经典模式图鉴中未出现且游戏中能遇到的部分卡牌，共 35 张
    - `egg_xxx`：彩蛋卡牌，游戏中不易遇到或通过特殊方式遇到
    - `extra_xxx`：一些卡牌/祝福的附属卡牌
    - `monster_xxx`：未出现在图鉴里的怪物卡牌
    - `newyear_xxx`：只有在春节活动中出现的活动卡牌
    - `ssr_xxx`：外婆卡组中的卡牌，出现率低或可能已被移除
    - `story_xxx`：剧情卡牌
- `card_ce`：通过 CE 修改出的部分废稿卡牌，共 83 张
- `card_ce_41`：官方愚人节动态中发布的 7 张卡牌，没想到真的做到了游戏里，通过 CE 获得
- `card_ce_ok`：卡面完整、效果完整的 CE 卡牌，共 24 张
- `card_diary`：小红帽日记模式图鉴中“全部”选项收录的卡牌，共 85 张
- `card_diary_extra`：小红帽日记模式中可以获得的 14 张初始怪物卡牌，图鉴中未出现
- `card_monster`：经典模式/小红帽日记图鉴中“怪物”选项收录的卡牌，共 149 张
- `card_skill`：部分角色的局内技能卡牌，共 17 张
- `card_upgrade`：部分相较于满星卡牌面有变化的未满星卡牌，共 48 张
- `excel`：群友通过逆向整理的卡牌信息 Excel 文件
- `kra_prjs`：使用 krita 制作的牌背文件
- `paints`：游戏中的 DLC 立绘

## 实体打印

月圆之夜的卡牌长宽比为3:2，适合使用 87x57mm 的卡牌尺寸；

经过测试，使用300g铜版纸，正面覆亮膜、背面覆哑膜的工艺效果和性价比较好

## 静态 Web 图鉴

网站使用 Vite、React 和 TypeScript，浏览图鉴无需后端或数据库。卡牌元数据按源图片目录拆分到 [`data/cards/`](data/cards/) 下的 JSON 文件，现有 Python 截图工具和源图片目录保持不变。

### 按文件夹划分卡牌分组

- `data/cards/base.json` → `assets/card_base/` → `group: "base"`（经典模式）。
- `data/cards/base_extra.json` → `assets/card_base_extra/` → `group: "base_extra"`（经典附属卡）。
- `data/cards/diary.json` → `assets/card_diary/` → `group: "diary"`（小红帽日记）。

三个文件结构相同，都是记录数组；此次仅拆分原有 845 条记录，保留各组内原始顺序和元数据，没有从其他图片目录导入新卡牌。旧 `data/cards.json` 和记录中的 `diary` 布尔字段已移除。

首页自动发现 `data/cards/*.json`，显示「全部卡牌」及每个文件对应的类别。以后新增 `assets/card_<group>/` 的类别时，只需添加同结构的 `data/cards/<group>.json`，并在每条记录中使用同名 `group`；无需修改首页标签或加载代码。新组默认显示组名，需要中文名称时可在 `scripts/card-groups.mjs` 的标签映射中补充。构建前会校验文件名、`group`、图片目录和关联卡牌。仅有图片目录、未添加 JSON 的卡牌不会被导入。

### 本地启动

需要 Node.js 22.18+ 或 24+。

```bash
npm install
npm run dev
```

打开终端显示的本地地址。启动时会先校验 JSON、检查图片是否存在，再生成列表用的 WebP 缩略图及可下载原图。新增或更换图片后，重新启动开发服务即可重新生成资源；仅修改元数据通常可直接热更新。

```bash
npm run validate  # 只检查元数据和源图片
npm test          # 检索、合并和校验逻辑测试
npm run build    # 校验、生成资源、类型检查、构建
npm run preview  # 预览构建结果
```

发布 `dist/` 即可部署到静态托管。资源使用相对地址，支持 GitHub Pages 的仓库子路径。构建只发布 JSON 引用的卡牌图片，不会把 Excel、CE 资源或整个 assets 目录打包。

### 补充卡牌数据

#### 网页编辑器

点击图鉴顶部右侧的「编辑卡牌」（`?editor`）即可编辑：

- 先通过「文件夹 / 分组」选择要编辑的 JSON，缩略图仅展示该组的记录，序号、拖动、上下移动及指定位置均对应组内顺序。切换组前若有未保存修改，会提示确认；可先保存或导出。
- 点击缩略图打开窗口，可修改名称、可获得职业（12 个固定职业复选框）、星级（无、一星、二星、三星单选，分别保存为 `null`、`1`、`2`、`3`）、类型（单选）、能耗、关联卡牌及可见性。分组跟随源图片目录和 JSON 文件，在窗口中只读，不跨文件夹移动卡牌。
- 名称在离开输入框或按 Enter 时应用，仅修改当前记录；分组、名称、星级全部相同才算重复。可见性同步本组同名卡牌的所有等级。若旧名称还有其他星级，关联引用保持不变；否则会更新本组内的引用。跨文件引用不会自动改写，若导致关联失效，需先移除旧关联，完成重命名后再添加。
- 关联卡牌可以搜索和多选。`base` 与 `base_extra` 保留原经典模式的跨目录关联，其他组只关联本组；同名时优先解析为同组卡牌，不串到日记。
- 使用 `npm run dev` 点击「保存到本地 JSON」，只写入运行开发服务的机器上当前分组的 `data/cards/<group>.json`，不会覆盖其他组的文件或顺序。支持本机、局域网和 OpenChamber 预览代理访问。接口通过临时令牌保护写入，禁止跨站请求及跨域读取令牌；生产构建不包含写文件服务。开发服务没有登录权限控制，请勿暴露到不可信网络或公网。
- 静态网站和 `npm run preview` 仅提供「导出 JSON」，下载当前组的 `<group>.json` 后替换 `data/cards/` 下的同名文件，再重新构建部署。
- 保存/导出前校验元数据、重复星级和关联卡牌。文件被其他程序修改时拒绝覆盖，可先导出当前编辑作为备份，再重新载入。
- 修改不会自动保存，离开时会提示。图片路径保持不变；添加新卡牌仍需手动维护 JSON 和图片。

每组 JSON 都是一个数组，每条记录代表一张卡的一个等级。例如 `base.json` 中的一条记录：

```json
{
  "name": "示例卡",
  "group": "base",
  "level": 1,
  "classes": ["职业A", "职业B"],
  "type": "攻击",
  "cost": 1,
  "image": "assets/card_base/示例卡1.png",
  "relatedCards": []
}
```

- `name`：完整卡名。同一分组内按名字合并卡牌等级。
- `group`：字符串，必须与所在 JSON 文件名一致，例如 `base`、`base_extra`、`diary`。不再使用 `diary` 布尔值。
- `level`：星级正整数；没有星级时填 `null`。不要根据文件名自动推断星级。
- `classes`：可获得职业数组；暂未核实填 `[]`，不代表所有职业通用。
- `type`：类型名称不含“牌”字，例如“攻击”“装备”“法力”“咒术”，名称请统一。
- `cost`：非负整数、`"X"` 或 `null`。`0` 为明确零费，`null` 表示不适用或尚未标注；目前不区分能耗资源种类。
- `image`：当前组的 `assets/card_<group>/` 目录下的真实图片相对路径。
- `relatedCards`：可关联分组内的卡牌完整名称；`base` 与 `base_extra` 可互相关联，其他组仅支持组内关联。不需要互相引用，也不会递归展开关系链。
- `hidden`：可选，默认 `false`。设为 `true` 时不出现在图鉴列表和名称搜索中，仍可通过关联按钮访问。同名各等级须保持一致。

同分组、同名、不同等级只占一个卡位，不同分组不会合并。默认展示已收录的最高等级；筛选时默认展示满足条件的最高等级。切换到不满足筛选的版本会显示提示。关联卡通过当前卡位中的按钮切换，不会额外展开卡位；关联卡本身是否独立出现在列表，由其 `hidden` 决定。

**收录数据仍需核实。** 部分职业、能耗和关联关系可能尚未补齐，请根据游戏资料逐步维护；关联按钮不代表已核实的游戏生成关系。

### 1000 张卡是否适合放在一个 JSON？

适合。每条记录即使按 1 KB 估算，1000 条也约 1 MB，压缩传输后通常更小。需要关注的是图片，不是 JSON 数组：网站单页展示全部筛选结果、列表使用约 360px 宽的 WebP 缩略图并懒加载，原图仅在详情或下载时请求。无需为了这个规模引入数据库。

生成目录 `public/assets/`、`public/thumbnails/` 不应手动存文件，构建时会重新生成。源图片始终维护在原始 `assets/` 下。
